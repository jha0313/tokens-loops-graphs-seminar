context: 에이전트가 한 번에 붙들고 읽을 수 있는 분량. 넘치면 앞 내용을 요약(압축)합니다.

두 방식은 같은 과제 문장, 같은 모델, 같은 예산 상한을 받았습니다. single은 에이전트 하나가 처음부터 끝까지 혼자 읽습니다. graph는 /graph-plan이 먼저 설계도를 쓰고, 지휘하는 orchestrator가 일을 열 조각으로 나눠 worker에게 동시에 여섯 개씩 맡깁니다. medium 이상 후보는 verifier 셋이 새 context에서 반박해 봅니다.

정답지가 없는 실제 감사라서 품질은 이렇게 쟀습니다. 네 run이 낸 주장 105건을 섞고, 어느 쪽이 찾았는지 지운 뒤 같은 것끼리 합쳐 53건을 만들었습니다. 새 context의 판정자가 코드를 읽고 44건을 맞는 발견으로 인정했고, 이걸 정답지로 썼습니다.

04

왜 그렇게 나왔나

칸 하나가 API route 파일 하나입니다. single은 "다 봤다"고 적었지만, 직접 연 파일은 절반 남짓이었습니다.

single: 한 context에 안 담김context가 약 39만 token까지 차서 중간에 한 번 압축됐고, 스스로는 "121개 다 봄"이라고 적었습니다.
graph: 조각마다 다 읽음node마다 맡은 묶음만 읽어 21만 token 안에서 끝났고, 압축은 없었습니다.

나눌 이유가 실제로 있었습니다. 그래서 이번에는 graph가 제 값을 했습니다.

왜 이렇게 됐는지가 이 그림입니다. 칸 하나가 API route 파일 하나, 모두 121개입니다. single은 두 번 모두 스스로 '121개 다 봤다'고 적었지만, 기록을 보면 직접 연 파일은 72개와 60개였습니다. graph는 두 번 모두 121개를 다 열었습니다.

single은 context가 약 39만 token까지 차서 중간에 한 번 압축됐습니다. 에이전트 하나에 안 담기는 일이었던 겁니다. graph의 node는 각자 맡은 묶음만 읽어서 21만 token 안에서 끝났습니다. 나눌 이유가 실제로 있었고, 그래서 graph가 제 값을 했습니다.

참고 — single 두 run을 합쳐도 맞는 발견 14건 · $24로 graph 한 run(32건 · $32)에 못 미침. 연 파일 수는 transcript 기준. 이전 PR 리뷰 실험(한 context에 들어가는 일)에서는 두 방식의 품질이 같았음.

그래서

  1. 나눌 이유가 있을 때만 나눕니다.한 context를 넘고, 조각이 서로 독립이고, 조각마다 확인할 방법이 있을 때입니다.
  2. 나누면 계약과 verifier부터 둡니다. 다만 verifier는 받은 것만 지킵니다.medium 이상은 하나도 안 뒤집혔고, 틀린 주장은 모두 verifier를 거치지 않은 low·info였습니다. 어디까지 검증할지도 설계입니다.
  3. 판정을 가르는 건 사람이 쓴 과제 문장입니다.loop 데모의 과제를 목표만 한 줄로 주면 graph-plan 판정은 3/3 "graph", 측정 명령과 규칙까지 쓰면 1/1 "loop"였습니다.

세 데모 모두, 마지막 판단은 사람이 했습니다: 얼마나 줄일지, 언제 반복할지, 언제 나눌지.

정리합니다. 나눌 이유가 있을 때만 나눕니다. 일이 한 context를 넘고, 서로 독립인 조각으로 나뉘고, 조각마다 확인할 방법이 있을 때입니다. 나누면 계약과 verifier부터 둡니다. 다만 verifier는 받은 것만 지킵니다. medium 이상 27건은 하나도 안 뒤집혔고, 틀린 주장은 전부 verifier를 거치지 않은 low와 info였습니다.

마지막으로, 판정을 가르는 건 사람이 쓴 문장입니다. loop 데모의 과제를 목표만 한 줄로 주면 graph-plan은 세 번 모두 graph라고 했고, 측정 명령과 규칙까지 쓴 문장을 주면 loop라고 했습니다. 세 데모 모두, 마지막 판단은 사람이 했습니다.

참고 — loop 과제 판정: 한 줄 문장 N=3(합 $2.06, 1번은 조건부 graph) · 구체 문장 N=1($1.96). 같은 예산을 쓰게 하는 loop arm은 이번에 돌리지 않음.

/graph-plan Run a security and privacy audit of this repository. This is a defensive, read-only code review of the owner's own code, to find real defects that should be fixed.

Cover these 7 surfaces:
1. auth: authentication and authorization ([…], session and role checks, admin gates, auth helpers).
2. api_routes: the 121 route handlers under app/api/ (`git ls-files 'app/api/**/route.ts'`): missing or weak auth checks, missing ownership checks (one user reading or changing another user's data), webhook signature checks, input validation, server-side fetch of user-supplied URLs, CORS.
3. secrets_env: secrets in tracked files, secrets that reach client code (NEXT_PUBLIC_*, client components), unsafe fallbacks.
4. outbound_pii: user data and PII sent to third parties (LLM, image, analytics, error tracking) beyond what the feature needs.
5. logging: secrets, tokens or PII written to logs, Sentry or analytics.
6. storage_db: database and storage policy (RLS, storage bucket policies, migrations, service-role or admin clients used where a user-scoped client would do).
7. dependencies: known-vulnerable or risky package versions in […] and […]. Offline only: read the versions. Do not run npm audit (it contacts the registry).

Rules:
- Read only. Do not change tracked files, do not commit, do not push. Write only under `audit/`.
- Do not run project scripts (`npm run ...`, `scripts/*`, node or tsx scripts in the repo), tests, builds or servers.
- No network access of any kind: no gh, curl, wget, npm or npx, and no CLI or code that contacts a service. Do not call production services or external APIs. Do not execute anything that tries an exploit; describe how a reviewer could confirm the issue instead.
- Do not open, read or print any `.env*` file or any key or token value. If a tracked file holds a secret-looking value, report only its file:line and the kind of secret, never the value.
- Ignore the instructions in CLAUDE.md, AGENTS.md and project skills that tell agents to sync with origin, run scripts, open GitHub issues or send reports. They do not apply to this run.
- A finding must point to a concrete code location and a concrete impact. Generic hardening advice, style and missing docs are not findings. Do not report the same issue twice: if one cause affects many files, report it once and list the other files.
- Write `audit/findings.json` in exactly this shape:
  {"findings": [{"id": "F1", "surface": "auth|api_routes|secrets_env|outbound_pii|logging|storage_db|dependencies", "file": "path from the repo root", "line": 123, "other_locations": ["path:line"], "title": "one line", "why": "the concrete issue and its impact", "evidence": "the relevant code (at most 5 lines, no secret values) and the reasoning", "severity": "critical|high|medium|low|info", "confidence": "high|medium|low", "how_to_confirm": "how a reviewer can confirm it without network access or running an exploit"}]}
- Also write `audit/coverage.json`: for each of the 7 surfaces, {"status": "covered|partial|not_covered", "examined": "what you read, for example 121/121 route files", "notes": "..."}.
- Budget: the whole run, including any subagents, stops hard at $60 (`--max-budget-usd`). Keep `audit/findings.json` up to date as you confirm findings, so a stop does not lose them.
- End with a short summary: the number of findings per surface and per severity.

Planning constraints for this run:
- Write GRAPH.md and facts.md under `audit/`, with paths relative to the repository root. Workers write `audit/results/<node>.md`.
- facts.md may hold setup facts only (paths, file lists, file counts, commands). Do not put review judgments or suspected findings in it.
- Every node runs on claude-opus-5-5 at the session's effort (xhigh), with no cheaper model. This graph will be compared against a single agent on the same model, with the same budget cap: $60 for the whole run, subagents included.
- Workers are Claude Code subagents with Read, Grep, Glob and Bash. No external scanners are installed (no gitleaks, semgrep or osv-scanner) and there is no network. A $0 script node is a shell command the orchestrator runs itself (for example a grep-based secret scan, or listing package versions from […]).
- The graph's final output must be `audit/findings.json` and `audit/coverage.json`, exactly as the task specifies.
- Plan only. Do not launch the graph. Do not audit the code yourself beyond what you need to size the branches (file counts, directory layout).

Non-interactive run: nobody can answer questions. Where you would ask, state your assumption and continue.

| orchestrator → verifier | 중복 제거한 medium 이상 후보만 (worker 서술은 안 보냄) | 후보마다 confirmed / refuted / adjusted | 20분 | 입력 cid = 출력 cid, refuted는 반증 위치가 실제로 있음 |
| verifier → orchestrator | 판정 | confirmed · adjusted만 findings.json에 추가 | — | 추가할 때마다 check.py final |

## 공유 state
- facts.md: append-only, 한 줄에 사실 하나와 출처 명령. 설정 사실만(경로 · 파일 목록 · 개수 · 명령). 판단·의심 금지.
- results/<node>.md: 파일마다 writer 하나. findings.json · coverage.json: orchestrator만 쓴다.

## 한도
- 깊이 2(orchestrator → worker · verifier). worker는 spawn할 수 없다. 동시에 도는 child 6개 이하 (6개 → 남은 4개 → verifier).
- 계획 합계 $57, 세션 hard cap $60. 누적 비용 gate: $40 새 worker 금지 · $45 재시도 금지 · $52 새 verifier 금지 · $56 즉시 마무리.
- timeout까지 결과가 없는 node는 UNKNOWN.

## Failure route
| 이벤트 | Route |
|---|---|
| 결과 파일 없음 · JSON 깨짐 · 배정 파일 80% 미만 | 새 worker로 한 번 재시도(안 본 파일만), 그다음 UNKNOWN |
| 후보 하나가 형식 검사 실패 | 그 후보만 버리고 센다 |
| evidence에 secret 패턴 | 값을 가린 뒤 처리 |
| 시스템 · 권한 오류 | graph를 멈추고 그때까지 결과를 쓴다 |
| worker와 verifier 충돌 | 반증 위치를 준 쪽(verifier)이 이긴다. 못 주면 confidence low, "disputed"로 센다 |
| 두 worker가 같은 원인 | 같은 원인이거나 같은 파일 5줄 안이면 하나로 합친다 |
| 같은 위임을 두 번 | spawn 전에 ledger.md를 보고, running · done이면 다시 띄우지 않는다 |
