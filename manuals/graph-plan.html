세 번째 스킬은 graph-plan입니다. 일을 여러 에이전트로 나눠 돌리는 걸 graph라고 부르는데요, 나누는 건 쉽지만 비용은 잘 안 보입니다. 이 스킬은 먼저 "정말 나눠야 하나"를 판정하고, 나눠야 할 때만 설계도 GRAPH.md를 써 줍니다.

PR 네 개를 리뷰시켰더니 품질은 똑같고 비용만 5.5배였습니다. 반대로 에이전트 하나에 다 안 들어가는 감사에서는 맞는 발견을 세 배 가까이 찾았습니다.

참고 — PR 4개 6/6 vs 6/6(5.5배), PR 10개 14/14 vs 14/14(2.7배). 감사는 실제 서비스 repo 하나, run당 맞는 발견 32 vs 11, 비용 2.7배, arm마다 2번.

01 · 한눈에 보는 설계도

질문 넷을 모두 지나야 graph입니다

위에서부터 답하고, 판정이 나면 거기서 멈춥니다. 대부분의 일은 중간에서 멈춥니다.

해 보기: 내 과제로 판정해 보기

layer test를 직접 해 보기: 내 과제는 prompt, loop, graph 중 무엇인가

SKILL.md Step 1의 질문을 순서대로 답하세요. 앞 질문에서 판정이 나면 뒤 질문은 보지 않습니다.

  1. Q1. 결과가 실행되기 전에 사람이 출력을 매번 전부 읽나요?

  2. Q2. "done"을 기계가 확인할 수 있나요? (query, 테스트, 지표, verdict rule)

  3. Q3. 한 agent의 context와 한 domain에 들어가나요?

    추측하지 말고 재세요. PR 10개, 2,592줄 리뷰도 246k에 들어갔습니다. [실험]

  4. Q4. 동시에, 서로 독립적으로 돌 수 있는 branch가 2개 이상인가요?

Q1부터 답하세요.

판정은 질문 네 개로 합니다. 사람이 출력을 전부 읽는다면 프롬프트로 충분합니다. 끝을 기계가 확인할 수 없다면, 나누기 전에 확인 방법부터 정해야 합니다. 에이전트 하나의 context에 다 들어간다면 loop로 충분합니다. 이건 감으로 답하지 말고 줄 수로 재 보세요.

마지막으로 동시에 따로 돌 갈래가 두 개 이상이어야 합니다. 네 질문을 다 통과해야 graph입니다.

참고 — PR 10개, 2,592줄 리뷰도 246k context에 들어감. "lint 40개 고쳐"는 2/2 loop로 판정, 억지로 나누면 비용 1.47배. Q3이 가장 자주 틀림: 경계선이면 single을 한 번 먼저 돌려 볼 것.

graph로 판정되면 받는 설계도

orchestrator(일을 나누고 모으는 에이전트)가 갈래마다 worker를 두고, 화살표마다 계약을 붙입니다.

graph로 판정되면 이런 설계도를 받습니다. orchestrator 하나가 일을 갈래마다 worker에게 나눕니다. 기계로 할 수 있는 일은 모델 없이 도는 script node로 둡니다. 실험에서 가장 쓸모 있던 node가 바로 이 0원짜리 스크립트였습니다.

화살표마다 계약이 붙습니다. 보낼 때는 질문과 사실 파일 경로, 받을 때는 판정, 근거, 확신도, 남은 질문. 새 context의 verifier가 주장을 반박해 보고, 확인된 것만 결과가 됩니다. 아래 줄은 한도입니다.

참고 — 깊이 ≤ 2(worker는 다시 나누지 않음), 동시 ≤ 6(넘으면 6개씩 차례로), node마다와 전체 예산, 시간 초과·연락 끊김은 UNKNOWN. 모으는 worker는 싼 모델, 검증은 강한 모델. script node는 PR 45쌍 병합본에 기존 테스트를 돌려 결함 3쌍을 표시.

02 · 실행과 받는 것

계획은 스킬이, 실행은 사람이

설치하고 부르기

bash · repo 루트에서 · loop-spec도 함께 
mkdir -p ~/.claude/skills
cp -R graph-plan loop-spec ~/.claude/skills/

/graph-plan <과제>로 부릅니다. "끝"을 무엇으로 확인할지 같이 적으면 Q2가 빨리 풀립니다.

받는 것 · graph일 때 GRAPH.md

  • 맨 위판정과 그것을 정한 질문
  • Nodesnode마다 모델 · 예산 · 출력 형식 · 끝 확인
  • Edges화살표마다 In · Out · Timeout · 검증
  • Limits깊이 · 동시 개수 · 예산, 실패했을 때 갈 곳
  • Launch새 세션에 붙여 넣을 orchestrator prompt

띄우기 전에 4가지

  • Q3을 줄 수로 재 봤나. 경계선이면 single을 먼저
  • 예산 추정은 방향만 본다
  • 스크립트로 할 수 있는 node를 먼저 찾았나
  • 비용은 자기 보고가 아니라 기록으로 잰다
복사해서 쓰기: 예시 프롬프트 3개
graph가 맞는 일: 병렬 테스트와 실패 설명
graph-plan으로 계획만 세워 줘. 생성된 변경에 비교 테스트 5개를 돌리고, 실패가 나오면 하나도 빠짐없이 원인을 설명하고 싶어. 실행은 하지 마.
loop로 충분한 일: lint 일괄 수정
graph-plan으로 lint 오류 고치는 작업을 subagent 여러 개로 나눠 줘. 파일이 40개야.

→ "graph 아님, loop"라고 답하고 loop-spec으로 넘깁니다.

경계선: 여러 PR 리뷰
graph-plan으로 열린 PR 10개를 리뷰하는 계획을 세워 줘. 결함을 빠짐없이 찾고 싶어. Q3(한 context에 들어가는지)는 추측하지 말고 전체 변경 줄 수로 재서 판단해 줘. 경계선이면 single로 한 번 먼저 돌려 보자고 해 줘.

설치할 때는 loop-spec도 같이 넣으세요. loop로 판정되면 그쪽으로 넘기기 때문입니다. 부를 때는 과제를 한 문장으로 주되, 끝을 무엇으로 확인할지 같이 적으면 판정이 빨라집니다. 계획만 세우고 실행은 하지 않습니다.

띄우기 전에 두 가지는 꼭 기억하세요. 스킬이 낸 예산 추정은 방향만 보세요. 그리고 비용은 orchestrator의 자기 보고가 아니라 기록으로 재세요. 실험에서 자기 보고는 실제의 20분의 1 수준이었습니다.

참고 — 예산 추정 $34.5 vs 실제 $14.4. orchestrator 자기 보고 0.89M token vs transcript 실측 18.8M. token-efficiency-summary가 main과 subagent 기록을 따로 셈. GRAPH.md에는 공유 상태(facts.md), 실패 경로, mermaid 그림도 들어감.

03 · 써 볼 만한 일

갈래가 따로 돌고, 답을 확인할 수 있는 일 세 가지

Q4에서 graph

여러 경로의 원인 분석

갈래 실행 경로마다 하나, 데이터를 만드는 쪽 하나, 저장하는 쪽 하나

확인 verifier가 원인 주장을 query로 확인하거나 반박

프롬프트
graph-plan으로 계획만 세워 줘. 이벤트 테이블의 country 컬럼이 일부 행에서만 비어 있어. 실행 경로별 branch, producer branch, schema/sink branch로 나누고, 각 branch는 EXPLAINS / DOES_NOT_EXPLAIN / UNKNOWN 중 하나와 근거 query를 돌려주게 해 줘. root cause 주장은 fresh context verifier가 query로 확인하게 하고, 실행은 하지 마.
Q3 · Q4에서 graph

후보를 나란히 비교하는 조사

갈래 후보마다 worker 하나. 모으는 일은 싼 모델

확인 verifier가 근거 링크가 결론을 받치는지 반박

프롬프트
graph-plan으로 우리 서비스에 쓸 job queue 후보 3개(A, B, C)를 비교하는 조사 계획을 세워 줘. 후보마다 worker 하나를 두고, 답은 verdict / evidence links / confidence / open questions 형식으로 받아 줘. verifier가 각 결론을 반박해 보게 하고, 질문끼리 묶여 있으면 나누지 말자고 말해 줘. 실행은 하지 마.
Q3 · Q4에서 graph

감사와 대량 리뷰

갈래 표면(인증, 저장소, 외부 API, 로그)마다 하나. secret scan 같은 일은 script node

확인 verifier가 발견 하나하나를 반박. 한 context에 들어가면 single로

프롬프트
graph-plan으로 이 repo의 보안·개인정보 감사 계획을 세워 줘. surface(인증, 저장소, 외부 API, 로그)마다 worker 하나, secret scan과 dependency audit은 스크립트 노드로 두고, verifier가 각 finding을 반박해 보게 해 줘. 먼저 전체가 한 context에 들어가는 규모인지 재 보고, 들어가면 single로 하자고 말해 줘. 실행은 하지 마.

규칙을 적용한 예입니다(실험 아님). 큰 기능을 통째로 나누면 갈래끼리 결정이 부딪힙니다. [공개] Cognition

graph를 써 볼 만한 일 세 가지입니다. 실행 경로가 여러 갈래인 원인 분석, 후보를 나란히 비교하는 조사, 그리고 보안 감사나 대량 리뷰처럼 에이전트 하나에 다 안 들어가는 검사입니다. 셋 다 갈래끼리 독립적이고, 각 갈래의 답을 정해진 형식과 verifier로 확인할 수 있습니다.

반대로 큰 기능을 통째로 나눠 맡기는 일은 조심하세요. 갈래끼리 서로의 결정을 보지 못해서 합칠 때 부딪힙니다.

참고 — 카드는 스킬 규칙을 적용한 예, 그대로 실험한 것 아님. 큰 기능은 API·schema 계약 고정, 모듈마다 테스트, committer 하나가 merge할 때만. 아니면 설계는 single, 구현은 loop.

04 · 언제 쓰나

나눌 이유가 있을 때만 나눕니다

기대할 수 있는 것

  • "graph 아님"을 먼저 말해 줍니다. lint 과제는 2/2 loop [실험]
  • 한 context를 넘는 일에서 더 넓게 봅니다. 실제 서비스 repo 하나 감사에서 맞는 발견 run당 32 vs 11 [실험]
  • 계약 · 한도 · verifier가 미리 적힌 설계도

기대하면 안 되는 것

  • 한 context 안에서 더 좋은 품질. PR 리뷰는 같은 품질에 비용 2.7–5.5배 [실험]
  • 정확한 예산. 추정은 방향만 맞습니다.
  • 실행. 계획만 세우고, 띄우는 것은 사람입니다.
근거: 수치를 잰 조건
  • [실험]발표 실험은 통제 실험입니다. 두 쪽 모두 Opus 5.5 xhigh, 같은 clone 커밋, 같은 과제, 바꾼 변수 1개, 셀당 N=2–3. 발표 실험
  • [실험]감사(데모 3): 결함을 심지 않은 실제 서비스 repo 하나를 읽기 전용으로 single 2번, graph 2번 감사했습니다. 발견을 모아 출처를 가린 채 판정했습니다. single은 API route 121개 중 60–72개만 열어 봤고 graph는 121개를 모두 봤습니다. 발견 1건당 비용은 $1.01 vs $1.09로 비슷했습니다. 발견 내용은 공개하지 않습니다. graph 데모
  • [공개]Anthropic의 multi-agent research 시스템은 내부 eval에서 단일 agent보다 90.2% 높았고, token은 chat의 약 15배를 썼습니다. Anthropic, 2025-06-13

정리하면, graph는 일이 에이전트 하나에 안 담기고, 갈래가 동시에 따로 돌 때만 씁니다. 실제 서비스 repo 하나를 감사했을 때 혼자 한 쪽은 route를 절반 정도만 열어 봤고, graph는 전부 봤습니다. 맞는 발견 1건당 비용은 비슷했습니다.

하지만 한 context에 들어가는 리뷰에서는 품질이 똑같고 비용만 몇 배 더 들었습니다. 나눌 이유가 있을 때만 나누고, 나누면 계약과 verifier부터 정하세요.

참고 — 감사: route 121개 중 single 60–72개, graph 121개. 1건당 graph $1.01 vs single $1.09. 발견 내용은 공개하지 않음(개수·비용만). 리뷰: 2.7–5.5배.
