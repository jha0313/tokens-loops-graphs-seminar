token-efficiency-summary

Claude Code 사용 기록을 읽어 돈이 어디로 갔는지 세고, 무엇부터 고칠지 순서를 정해 주는 읽기 전용 스킬입니다.

실행 
/token-efficiency-summary --last 30d --aggregate

최근 30일을 모아 봅니다. 인자 없이 부르면 지금 세션만 봅니다.

받는 것
30일 기록 → 모델 호출마다 정가로 셈
↓ 표 보고서 (원하면 HTML 대시보드)
  • 쓴 돈토큰 표와 추정 비용
  • 새는 곳cache가 깨진 곳, 낭비 패턴
  • 고칠 것노력 대비 금액이 큰 순서
근거
−11%

위의 셋을 고치고 같은 작업을 다시 돌린 비용(중앙값). 통과는 7/9 → 9/9. [실험] 토큰 데모

이럴 때 쓰세요비용이 어디로 가는지, 무엇부터 고칠지 알고 싶을 때

이럴 땐 쓰지 마세요"이만큼 아낀다"는 확정 금액이 필요할 때. 금액은 상한이고, 효과는 다시 재야 압니다.

첫 번째 스킬은 token-efficiency-summary입니다. Claude Code를 쓰면 세션마다 기록 파일이 남는데요, 이 스킬은 그 기록을 읽어서 돈이 어디로 갔는지 모델 호출 하나하나 셉니다. 그리고 무엇부터 고치면 좋을지 순서까지 정해 줍니다. 읽기만 하고, 아무것도 고치지 않습니다.

실제로 위의 셋을 고치고 같은 작업을 다시 돌려 보니 비용 중앙값이 11% 줄었고, 통과도 아홉 번 중 일곱에서 아홉으로 늘었습니다. 다만 표본이 작아서 우연일 수도 있습니다.

참고 — 과제 3개 × 3번 × 고치기 전·후 = 18 run, Opus 5.5 xhigh, 사람 개입 0. 평균은 −26%지만 비싼 run 하나 탓이라 중앙값을 씀.

01 · 한눈에 보는 흐름

재고, 고치고, 다시 잽니다

스킬은 재는 일만 합니다. 고르고 고치는 일은 사람이 하고, 효과는 같은 작업을 다시 돌려 확인합니다.

그림으로 보면 이렇게 돕니다. 30일 기록을 넣으면 스킬이 분석합니다. cache가 어디서 깨졌는지, 어떤 낭비 패턴이 있는지 보고, 새는 돈을 금액 순으로 줄 세웁니다. 결과는 대시보드 한 장으로도 받을 수 있습니다.

여기까지가 스킬의 일이고, 아래 줄은 사람의 일입니다. 위에서 셋만 골라 고치고, 같은 작업을 다시 돌려서 정말 줄었는지 잽니다. 핵심은 마지막 점선입니다. 다시 재지 않으면, 고친 게 효과가 있었는지 알 수 없습니다.

참고 — 대시보드는 기본으로 session ID, 파일 경로, prompt 내용을 넣지 않음. --dashboard-ids를 줄 때만 비용 상위 ID를 넣음.

청구서는 네 줄입니다

token 수가 같아도 어느 줄에 찍혔는지에 따라 값이 다릅니다. 그래서 분석기는 모델 호출마다 네 줄을 따로 셉니다.

해 보기: 내 숫자로 청구서 계산하기

직접 계산해 보기

분석기와 같은 방식(TTL별 정가)으로 추정 비용과 "cache가 없었다면"을 나란히 보여 줍니다. 계산은 이 페이지 안에서만 합니다.

값을 넣으면 계산합니다.

토큰 비중

비용 비중

왜 호출마다 세야 하는지 보겠습니다. 청구서는 네 줄입니다. 입력, cache 쓰기, cache 읽기, 출력. 입력 값을 1로 두면 cache에 저장하는 건 1.25배에서 2배, 다시 읽는 건 20분의 1, 출력은 5배입니다.

그래서 token 수가 같아도 어느 줄에 찍혔는지에 따라 돈이 완전히 달라집니다. token 대부분이 싼 읽기에 찍히고, 돈은 비싼 쓰기와 출력에서 나가는 일이 흔합니다. 이 스킬은 이 네 줄을 호출마다 따로 셉니다.

참고 — Opus 5.5 정가(1M당): 입력 $4, 5분 쓰기 $5, 1시간 쓰기 $8, 읽기 $0.20, 출력 $20. 읽기 비율은 모델마다 1/10–1/40. graph 실험 기록: cache 읽기가 token 94% · 비용 26%, 출력이 token 1.5% · 비용 42%. 구독 청구액이 아니라 정가 추정.

플래그는 섞어 쓸 수 있습니다. --last 없이 --aggregate나 --project를 쓰면 최근 30일을 봅니다. [설계]

설치는 폴더 하나를 복사하면 끝입니다. python3만 있으면 되고, 패키지 설치나 네트워크 접속은 없습니다.

부르는 법은 세 줄만 기억하시면 됩니다. 인자 없이 부르면 지금 세션, last 30d와 aggregate를 붙이면 한 달을 모아서, compare에 세션 두 개를 주면 고치기 전과 후를 나란히 봅니다. 공유할 화면이 필요하면 dashboard에 파일 이름을 붙이세요. 말로 "지난 30일 집계해 줘"라고 해도 됩니다.

참고 — 첫 실행 때 분석기를 ~/.claude/scripts/analyze-tokens.py로 복사하고, 설치본과 다를 때만 덮어씀. 프로젝트 하나에서만 쓰려면 그 repo의 .claude/skills/에 둠.

03 · 받는 것

보고서는 다섯 질문에 답합니다

  1. 얼마 썼나토큰 표와 추정 비용(공개 정가 기준)
  2. cache가 얼마나 아꼈나"cache가 없었다면 $X" 한 줄
  3. cache가 왜 깨졌나원인별 횟수, 1시간 TTL로 바꾸면 어떻게 되는지
  4. 어디서 샜나낭비 패턴 최대 15개, 패턴마다 "최대 $X"
  5. 무엇부터 고치나30일 금액 · 노력 · 위험, 노력 대비 금액이 큰 순서

금액은 상한입니다

보고서는 "$X를 아낀다"가 아니라 "최대 $X"라고 씁니다. 맨 위 한두 개만 고치고, 같은 작업으로 다시 재세요.

보고서는 위에서부터 다섯 가지 질문에 답합니다. 얼마 썼나, cache가 얼마나 아껴 줬나, cache가 왜 깨졌나, 어디서 샜나, 그리고 무엇부터 고치나. 마지막 목록은 30일 금액과 노력, 위험을 같이 보여 주고, 노력 대비 금액이 큰 순서로 줄 세웁니다.

금액을 읽을 때는 한 가지만 기억하세요. 보고서는 "최대 얼마"라고 씁니다. 확정 절감액이 아니라 상한입니다. 그래서 맨 위 한두 개만 고치고 다시 재는 겁니다.

참고 — 탐지기 21개(기본), --full이면 23개. 한 사용자의 30일 예: 총 $1,009.53, cache가 없었다면 $8,918(8.8배), 세션 도중 cache break 171회 $172.55, 그중 59%가 subagent 5분 TTL 만료.

04 · 언제 쓰나

추정 1위가 내 1위는 아닙니다

이럴 때 쓰세요

  • 비용이 어디로 가는지 모델 호출 단위로 보고 싶을 때
  • 무엇부터 고칠지 순서가 필요할 때
  • 고치기 전·후를 같은 작업으로 비교할 때

기대하면 안 되는 것

  • 확정 절감액. 금액은 "최대 $X" 상한입니다.
  • 추정 1위가 내 작업에서도 1위라는 보장. 데모의 1위 수정은 효과가 0이었습니다. [실험]
  • 구독 청구액. 공개 정가로 계산한 추정입니다.
근거: 수치를 잰 조건
  • [실험]토큰 데모: 실제 과제 3개를 고치기 전·후로 3번씩, 모두 18번 사람 없이 돌렸습니다. 두 쪽 모두 Opus 5.5 xhigh, 매번 새 clone. 세 수정을 함께 켜서 수정별 몫은 따로 재지 않았습니다. 토큰 데모
  • [실험]ROI 1위였던 subagent cache TTL 1시간은 효과가 없었습니다. subagent 호출 사이 간격이 가장 길어도 226초라 5분 TTL이 한 번도 끝나지 않았고, 저장 단가만 올랐습니다(run당 약 +$0.18). 줄어든 몫은 짧아진 prefix와 줄어든 호출·읽기에서 나왔습니다.
  • [실험]통과 7/9 → 9/9는 N이 작아 우연일 수 있습니다(Fisher 양측 p ≈ 0.47).

정리하면, 비용이 어디로 가는지와 고칠 순서가 궁금할 때 쓰시면 됩니다. 반대로 "이만큼 아낄 수 있다"는 확정 금액이 필요할 때는 맞지 않습니다.

데모에서 재미있었던 건, 추정 1위였던 수정이 실제로는 효과가 0이었다는 점입니다. 그 작업에서는 cache가 식을 만큼 오래 쉬는 구간이 없었습니다. 추정 1위가 내 1위는 아닙니다. 그러니 꼭 같은 작업으로 다시 재 보세요.

참고 — subagent 호출 간격 최대 226초, 5분 TTL 만료 0회. 1시간 TTL은 저장 단가만 $5 → $8로 올림. 통과율 차이는 p ≈ 0.47.
