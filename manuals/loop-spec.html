loop-spec

에이전트에게 반복 작업을 맡길 때, "끝났다"를 에이전트 대신 check.sh(끝났는지 검사하는 스크립트)가 말하게 하는 loop 설계도를 써 줍니다.

실행 
/loop-spec <목표 한 문장>

설계만 합니다. loop는 사람이 시작합니다.

받는 것
LOOP.md check.sh state.md /goal 한 줄
↓ check.sh 마지막 줄이 판정
  • LOOP-DONE끝
  • LOOP-CONTINUE다음 iteration
  • LOOP-BLOCKED멈추고 사람에게
근거
2/3 → 0/3

측정이 흔들리는 빌드 단축 과제에서 "목표를 넘었다"는 과장 보고. 프롬프트 하나 2/3, loop 0/3. [실험] 발표 실험

이럴 때 쓰세요테스트 통과, 빌드 시간 단축처럼 "끝"을 테스트·exit code·지표로 판정할 수 있는 반복 작업

이럴 땐 쓰지 마세요"README를 더 좋게"처럼 기계가 "끝"을 판정할 수 없는 목표. 스킬이 거절하고 대안을 냅니다.

두 번째 스킬은 loop-spec입니다. 에이전트에게 반복 작업을 맡기면 가장 무서운 말이 "다 됐습니다"입니다. 정말 됐는지 사람이 매번 볼 수는 없으니까요. 이 스킬은 그 "끝났다"를 에이전트 대신 check.sh라는 검사 스크립트가 말하게 하는 loop 설계도를 써 줍니다. 설계만 하고, 시작은 사람이 합니다.

측정이 흔들리는 빌드 단축 과제를 줘 봤더니, 프롬프트 하나로 시킨 쪽은 세 번 중 두 번 "목표를 넘었다"고 과장했고, loop는 한 번도 그러지 않았습니다.

참고 — 셀당 N=3, Opus 5.5 xhigh, 같은 clone 커밋. 비용은 loop가 1.45–1.7배, 실제 단축 품질은 같았음.

01 · 한눈에 보는 흐름

스킬이 설계하고, 사람이 시작합니다

목표 한 문장에서 시작해 파일 두 개와 /goal 한 줄로 끝납니다. 기계가 판정할 "끝"이 없으면 여기서 멈춥니다.

만드는 과정은 네 칸입니다. 목표를 한 문장으로 주고, 스킬이 repo에서 못 찾은 것만 묻는 질문에 답합니다. 그러면 스킬이 규칙 파일 LOOP.md와 판정 스크립트 check.sh를 씁니다. 마지막으로 /goal 한 줄을 받아 붙여 넣는 순간 loop가 시작됩니다.

중요한 건 아래 빨간 점선입니다. "README를 더 좋게"처럼 끝을 기계가 판정할 수 없는 목표는 여기서 거절하고, 대신 쓸 수 있는 방법 세 가지를 냅니다.

참고 — 끝 판정은 exit code, 테스트·CI, 지표 임계값, schema, byte 동일 중 하나여야 함. 대안: 지표 스크립트 / 리뷰어 + 기준표(원래 목표보다 약함) / 단계마다 사람 확인(/loop). /goal 조건은 4,000자까지.

한 바퀴는 이렇게 돕니다

판정하는 것은 check.sh의 마지막 줄 하나입니다. 세 단어 중 무엇이 나올지 에이전트가 직접 쓸 수 없습니다.

해 보기: 내 숫자로 채택 규칙 계산하기

채택 규칙 계산기

낮을수록 좋은 지표(예: 초 단위 빌드 시간)를 가정합니다. 모든 값은 같은 단위로 넣으세요. 이 페이지 안에서만 계산합니다.

baseline 중앙값, spread, 후보 중앙값을 넣으세요.

돌기 시작하면 한 바퀴가 이렇게 생겼습니다. 에이전트가 LOOP.md 규칙대로 일하고, 한 일을 state.md에 적습니다. 그다음 check.sh를 돌리고, 그 마지막 줄 하나가 판정입니다. 계속이면 다음 바퀴, 끝이면 결과 보고, 막혔으면 멈추고 사람을 부릅니다.

지표를 줄이는 loop라면 여러 번 재서 중앙값으로 비교합니다. 흔들림의 두 배보다 크게 좋아지고 guard도 통과할 때만 채택하고, 아니면 되돌립니다.

참고 — exit 0 LOOP-DONE, exit 1 LOOP-CONTINUE, exit 2 LOOP-BLOCKED. 측정은 기본 3번. 진전 없는 iteration 3번 → replan 한 번 → 그래도 없으면 멈춤. 예산 소진, 같은 실패 3번, 경계 밖 행동도 멈춤.

02 · 실행과 받는 것

목표 한 문장을 주면, 파일과 /goal 한 줄이 옵니다

설치하고 부르기

bash · repo 루트에서 
mkdir -p ~/.claude/skills
cp -R loop-spec ~/.claude/skills/

/loop-spec <목표>로 부르거나 "loop-spec으로 …"라고 말합니다. 예산과 절대 하면 안 되는 행동을 같이 적으면 질문이 줄어듭니다.

받는 것 · .loop/<이름>/ 아래

  • LOOP.md규칙: 목표 · 끝 · 멈춤 · 권한 경계 (9문항)
  • check.sh판정: 마지막 줄 하나
  • state.md기억: 시도한 것과 이유, 다음 바퀴가 읽음
  • results.tsv지표를 줄이는 loop일 때 measure.sh로 잰 기록
  • /goal 한 줄붙여 넣으면 시작 (4,000자 이내)

시작하기 전에 4가지

  • main checkout이 아니라 clone이나 worktree에서 돌리나
  • check.sh를 손으로 한 번 돌려 봤나
  • 다른 clone에서 깨질 경로·hash가 박혀 있지 않나
  • 붙여 넣은 뒤 "Goal set"이 떴나
복사해서 쓰기: 예시 프롬프트 3개
fix-until-green: 테스트가 다 통과할 때까지
loop-spec으로 tests/ 아래 테스트가 모두 통과할 때까지 고치는 loop를 설계해 줘. 예산은 최대 10 iteration, 2시간이야. push와 merge는 절대 하지 마. 시작은 내가 할게.
hill-climb: 지표를 목표까지
loop-spec으로 빌드 시간을 20% 줄이는 loop를 만들어 줘. 빌드 결과물은 byte 단위로 같아야 해. 예산은 15 iteration, 4시간.
판정할 수 없는 목표
loop-spec으로 README를 더 좋게 만드는 loop를 돌려 줘.

→ "No machine-checkable done"으로 거절하고 대안 3개를 냅니다.

설치는 폴더 복사 한 번이고, 부를 때는 목표를 한 문장으로 줍니다. 예산과 절대 하면 안 되는 행동을 같이 말해 두면 질문이 줄어듭니다. 받는 것은 .loop 폴더 아래 파일 몇 개와 /goal 한 줄입니다.

시작하기 전에 네 가지만 확인하세요. clone이나 worktree에서 돌리는지, check.sh를 손으로 한 번 돌려 봤는지, 다른 clone에서 깨질 값이 박혀 있지 않은지, 붙여 넣은 뒤 "Goal set"이 떴는지.

참고 — /goal이 명령이 아니라 글자로 들어가 1시간 18분 동안 아무 일도 안 한 사례가 있음. headless claude -p에는 --max-turns 상한을 꼭 줌. loop는 push·merge하지 않음.

03 · 써 볼 만한 일

"끝"을 스크립트가 말할 수 있는 일 세 가지

fix-until-green

PR의 CI가 전부 green이 될 때까지

끝 CI check가 모두 green, 테스트 수는 그대로, skip·삭제 없음

사람을 부를 때 권한·CI 장애, 같은 실패 3번. merge는 사람이

프롬프트
loop-spec으로 PR #123의 CI가 전부 green이 될 때까지 실패를 하나씩 고치는 loop를 설계해 줘. 테스트 수가 줄면 안 되고, 테스트를 skip하거나 지우면 안 돼. CI는 10분 간격 /loop로 확인하고 sleep으로 기다리지 마. merge는 내가 할게. push를 이 PR 브랜치에만 허용할지는 먼저 나한테 물어봐 줘.
hill-climb

빌드·테스트 시간을 목표까지

끝 채택된 중앙값이 목표 이하, guard 통과

사람을 부를 때 측정 실패, 예산 소진, 진전 없는 3번

프롬프트
loop-spec으로 test suite 실행 시간을 줄이는 hill-climb loop를 설계해 줘. 목표는 baseline 대비 25% 단축이야. 통과하는 테스트 목록은 지금과 똑같아야 해. 입력은 현재 커밋으로 고정하고, 측정은 다른 작업이 없을 때만 해. 예산은 12 iteration, 3시간.
watch

배포가 끝날 때까지 지켜보기

끝 배포 파이프라인이 성공 상태에 닿음

사람을 부를 때 실패·alarm·권한 오류는 바로. rollback은 하지 않음

프롬프트
loop-spec으로 방금 시작한 배포 파이프라인이 끝날 때까지 5분마다 상태를 확인하는 loop를 설계해 줘. 성공하면 끝, 진행 중이면 계속, 실패하거나 alarm이 뜨거나 권한 오류가 나면 바로 멈추고 나를 불러. rollback이나 재시도는 절대 하지 마.

스킬 규칙을 적용한 예입니다. 카드 그대로 실험한 것은 아닙니다.

그럼 어디에 써 볼까요. 세 가지를 추천합니다. 첫째, PR의 CI가 전부 green이 될 때까지 실패를 하나씩 고치는 일. 둘째, 빌드나 테스트 시간처럼 스크립트로 재는 지표를 목표까지 줄이는 일. 셋째, 배포가 끝날 때까지 상태만 보다가 문제가 생기면 사람을 부르는 일.

셋 다 "끝"을 스크립트가 판정할 수 있다는 게 공통점입니다. 카드를 펼치면 바로 복사해 쓸 프롬프트가 있습니다.

참고 — PR 카드는 push 권한을 먼저 정할 것(스킬 기본은 push 금지). CI 대기는 /loop 간격으로 깨우고 sleep-poll은 금지. hill-climb은 다른 작업과 겹치지 않게 혼자 돌릴 것(겹친 run은 noise 29%로 진짜 19% 개선을 거절).

04 · 언제 쓰나

loop가 사 주는 것은 속도가 아니라 정직함입니다

이럴 때 쓰세요

  • "끝"을 테스트나 지표 스크립트로 판정할 수 있는 반복 작업
  • 사람 없이 오래 맡겨야 하는데, 거짓 "끝"이 걱정될 때
  • 멈출 조건(예산, 같은 실패, 막힘)을 미리 정해 두고 싶을 때

기대하면 안 되는 것

  • 더 싼 결과. 비용은 1.45–1.7배, 품질은 같았습니다. [실험]
  • 더 빠른 결과. 썸네일 시간 데모의 결론은 "이번엔 single로 충분"이었습니다. [실험] loop 데모
  • 판정할 수 없는 목표. 스킬이 거절하고 대안 3개를 냅니다.
근거: 수치를 잰 조건
  • [실험]발표 실험은 통제 실험입니다. 두 쪽 모두 Opus 5.5 xhigh, 같은 clone 커밋, 같은 과제, 바꾼 변수 1개, 셀당 N=3. N이 작아 효과 크기를 주장할 수 없습니다. 발표 실험
  • [실험]썸네일 데모: 기록 재생(replay)에서는 single이 목표를 넘었고 loop는 중간에 BLOCKED로 멈췄습니다. single이 더 줄인 몫은 재생에서만 맞는 추측이었고, 실제 API로는 두 쪽을 가르지 못했습니다. 거짓 "끝"은 0이었습니다. loop 데모
  • [설계]시작, push, merge는 사람이 합니다. 스킬은 설계 파일만 씁니다.

정리하겠습니다. loop는 "끝"을 기계가 말할 수 있고, 사람 없이 오래 맡겨야 할 때 겁니다. 대신 싸지지는 않습니다. 실험에서 비용은 1.5배 안팎이었고, 결과 품질은 프롬프트 하나와 같았습니다.

썸네일 생성 시간을 줄여 본 데모도 결론은 "이번엔 single로 충분"이었습니다. loop가 사 주는 건 속도가 아니라 정직함입니다. 거짓 "끝"이 없다는 것, 그게 오래 맡길 수 있는 이유입니다.

참고 — 비용 1.45–1.7배(N=3). 썸네일 데모: replay에서 single −26%, loop −7%에서 BLOCKED. 실제 API로는 두 arm을 가르지 못함. 거짓 "끝" 0.
